1 · Come funziona, in breve

Il Professore Digitale vive su GitHub in tre posti, che lavorano insieme:

📁 Il repositoryi sorgenti del programma, con tutta la storia delle versioni. Si carica con GitHub Desktop.
→
📦 La Release«la scatola» di ogni versione: installatore Windows, pacchetto Linux, versione da chiavetta, sito. Si crea dal sito di GitHub.
→
🌐 Il sitola pagina per tutti, l'app per telefono e il file degli aggiornamenti. Si pubblica da solo.

Perché tre posti e non uno: GitHub rifiuta i file più grandi di 100 MB nel repository e nel sito, e i nostri installatori pesano più di 200 MB (dentro ci sono le voci naturali). Le Release invece accettano file fino a 2 GB l'uno. Il programma è già stato preparato per questo: il file degli aggiornamenti manda i PC a scaricare dalla Release, controllando sempre l'impronta SHA-256.

Le parole da conoscere

Repository (o «repo»)
La cartella del progetto su GitHub, con la storia di ogni modifica.
Commit
Una «fotografia» delle modifiche, con una frase che le descrive.
Push
Spedire i commit dal vostro PC a GitHub.
Branch «main»
La linea principale del progetto. Noi usiamo solo questa.
Tag
Un'etichetta su un commit: v3.5.1 = «qui c'è la versione 3.5.1».
Release
La pagina di una versione con i file da scaricare (si chiamano assets).
GitHub Pages
Il sito gratuito: danilodauria.github.io/professore-digitale.
Actions
I «robot» di GitHub: il nostro pubblica il sito quando esce una Release.
Cosa vi serve
  • L'account GitHub danilodauria (fatto) e GitHub Desktop aperto con quell'account (fatto: in alto a sinistra, File → Options → Accounts deve mostrare danilodauria).
  • La cartella Download\ProfessoreDigitale-3.5.1 con le parti .parte e UNISCI-E-ESTRAI.bat.
  • Un browser (Edge o Chrome) collegato a github.com con lo stesso account.
  • Circa un'ora la prima volta (quasi tutto è attesa dei caricamenti: ~1 GB). Le volte successive, 15 minuti.
Regola d'oroSu GitHub non si mette mai: il numero della carta, password, il certificato di firma del codice o la chiave GPG. Il repository e il sito sono pubblici: li può vedere chiunque. L'IBAN e il link PayPal della pagina «Sostieni» sono fatti apposta per essere pubblici.

2 · Preparare i file ricevuti

  1. Aprite Esplora file → Download\ProfessoreDigitale-3.5.1.
  2. Doppio clic su UNISCI-E-ESTRAI.bat. Se Windows mostra «Windows ha protetto il PC», cliccate Ulteriori informazioni → Esegui comunque (è il nostro file: lo potete aprire con il Blocco note per vedere cosa fa). Riunisce le parti, controlla le impronte (devono comparire solo OK) ed estrae tutto. Ci vogliono alcuni minuti.
  3. Alla fine, nella cartella professore-digitale-3.5.1-github trovate due cartelle:
    CartellaContieneDove va
    professore-digitaleI sorgenti del programma, con la storia e le impostazioni di git (una cartella nascosta .git: non toccatela).Nel repository, con GitHub Desktop (capitoli 3–4)
    rilascio-3.5.15 file: ProfessoreDigitale-Setup-3.5.1.exe, professore-digitale_3.5.1_all.deb, professore-digitale-windows-3.5.1.zip, sito-3.5.1.zip, NOTE-3.5.1.mdNella Release, dal sito di GitHub (capitolo 6)
  4. Spostate la cartella professore-digitale in Documenti\GitHub (se la cartella GitHub non c'è, createla: tasto destro → Nuovo → Cartella). Il percorso finale sarà Documenti\GitHub\professore-digitale.
Perché spostarlaÈ la cartella «di lavoro» che GitHub Desktop terrà d'occhio per sempre. In Documenti è al sicuro dalle pulizie della cartella Download. Non zippatela e non rinominatela dopo averla aggiunta a GitHub Desktop.

3 · Creare il repository vuoto su GitHub SOLO LA PRIMA VOLTA

  1. Nel browser andate su github.com (già entrati con l'account danilodauria). In alto a destra cliccate + → New repository.
  2. Compilate così:
    Create a new repository · github.com/new
    Ownerdanilodauria
    Repository nameprofessore-digitale ← esattamente così, minuscolo, con il trattino
    DescriptionCattedra Digitale Portatile – alfabetizzazione digitale offline

    Add READMENO   .gitignore: None · License: None ← tutto vuoto
    Il repository deve nascere vuoto: README, licenza e .gitignore sono già nei sorgenti.
  3. Cliccate Create repository. Si apre una pagina con le istruzioni «Quick setup»: non serve seguirle, chiudetela pure.

Il nome conta: il programma cerca gli aggiornamenti su danilodauria.github.io/professore-digitale e scarica da github.com/danilodauria/professore-digitale/releases. Se il nome fosse diverso, gli aggiornamenti non arriverebbero.

4 · Caricare i sorgenti con GitHub Desktop

4a · Aggiungere la cartella SOLO LA PRIMA VOLTA

  1. In GitHub Desktop: menu File → Add local repository… (oppure Ctrl+O).
  2. Choose… → selezionate Documenti\GitHub\professore-digitale → Add repository.
  3. In alto a sinistra ora c'è Current repository: professore-digitale e Current branch: main. La colonna «Changes» deve dire 0 changed files (i file sono già tutti in un commit: la versione 3.5.1 l'ho preparata io).

4b · Spedire i sorgenti a GitHub

  1. In alto, al centro della barra, c'è un pulsante: la prima volta si chiama ⬆ Publish branch, le volte successive ⬆ Push origin. Cliccatelo.
  2. Attendete che finisca (circa 90 MB: da 1 a 10 minuti secondo la connessione). Quando ha finito, il pulsante diventa Fetch origin.
  3. Controllo: nel browser aprite github.com/danilodauria/professore-digitale. Dovete vedere le cartelle (src, docs, windows…) e sotto la presentazione del progetto (il file README).
Se GitHub Desktop propone «Publish repository» invece di «Publish branch» Vuol dire che la cartella non sa ancora dove spedire. Nessun problema: cliccate Publish repository, lasciate il nome professore-digitale, togliete la spunta a «Keep this code private», Organization: None, poi Publish repository. Se risponde che il nome esiste già, il repository del capitolo 3 c'è: chiudete, menu Repository → Repository settings → Remote e scrivete https://github.com/danilodauria/professore-digitale.git, Save, poi Publish branch.

GitHub Desktop spedisce anche le etichette delle versioni (i tag, es. v3.5.1). Se non comparissero su GitHub non è un problema: il tag lo crea la Release del capitolo 6.

5 · Accendere il sito (GitHub Pages) SOLO LA PRIMA VOLTA

  1. Su github.com/danilodauria/professore-digitale cliccate ⚙ Settings (in alto, ultima voce della barra del repository).
  2. Nella colonna a sinistra, sezione «Code and automation», cliccate Pages.
  3. In Build and deployment → Source scegliete GitHub Actions (non «Deploy from a branch»). Non serve scegliere nessun modello proposto: il nostro «robot» c'è già nei sorgenti (.github/workflows/pubblica-sito.yml).
  4. Fine. Il sito comparirà da solo dopo la prima Release (capitolo 6).
Controllo facoltativoCliccate la scheda Actions del repository: deve comparire il workflow «Pubblica il sito». Se GitHub chiede di abilitare le Actions («I understand my workflows, go ahead and enable them»), confermate.

6 · Pubblicare la versione: la Release

  1. Sulla pagina del repository, a destra, cliccate Releases (oppure aprite github.com/danilodauria/professore-digitale/releases).
  2. Cliccate Draft a new release (la prima volta: Create a new release).
  3. Choose a tag: se nell'elenco c'è v3.5.1, sceglietelo. Se non c'è, scrivete v3.5.1 e cliccate + Create new tag: v3.5.1 on publish; Target deve essere main. La «v» minuscola davanti è obbligatoria.
  4. Release title: Professore Digitale 3.5.1.
  5. Describe this release: aprite NOTE-3.5.1.md della cartella rilascio-3.5.1 con il Blocco note, selezionate tutto (Ctrl+A), copiate (Ctrl+C) e incollate qui (Ctrl+V).
  6. Trascinate nel riquadro «Attach binaries by dropping them here or selecting them» questi 4 file della cartella rilascio-3.5.1:
    FilePesoA cosa serve
    ProfessoreDigitale-Setup-3.5.1.exe~215 MBInstallatore per Windows (da XP a 11)
    professore-digitale_3.5.1_all.deb~230 MBPacchetto per Linux
    professore-digitale-windows-3.5.1.zip~250 MBVersione Windows da chiavetta
    sito-3.5.1.zip~40 MBIl sito: lo prende il «robot» e lo mette online. Non dimenticatelo!
    Ogni file mostra una barra di avanzamento. Aspettate che siano finite tutte e quattro (anche mezz'ora) senza chiudere la pagina.
  7. Lasciate «Set as the latest release» spuntato e «Set as a pre-release» senza spunta.
  8. Cliccate Publish release.
Se dovete interrompereSave draft salva tutto come bozza, file compresi: la ritrovate in Releases e la pubblicate dopo. I nomi dei file non vanno cambiati: il programma li cerca esattamente così.

7 · Controllare che tutto funzioni

  1. Il robot: scheda Actions → «Pubblica il sito». Dopo 1–3 minuti deve avere il pallino verde ✔. Se è rosso ✘, vedete «Se qualcosa va storto».
  2. Il sito: aprite https://danilodauria.github.io/professore-digitale/. Deve comparire la pagina del Professore con «versione 3.5.1» e i pulsanti per scaricare. Provate a cliccare Scarica per Windows: il download deve partire (da github.com).
  3. Il file degli aggiornamenti: https://danilodauria.github.io/professore-digitale/aggiornamenti.json deve mostrare "versione": "3.5.1".
  4. L'app per telefono: inquadrate il QR code della pagina con un telefono; si apre il Professore, che si può aggiungere alla schermata Home.
  5. Da un PC con il Professore: Impostazioni → Aggiornamenti → 🌐 Controlla aggiornamenti. Deve annunciare la 3.5.1 (su un PC con una versione precedente).

8 · Le versioni successive OGNI VOLTA

Quando vi consegno una nuova versione (es. 3.6.0) trovate in Download la cartella ProfessoreDigitale-3.6.0. I capitoli 3 e 5 non si ripetono più.

  1. Preparare: doppio clic su UNISCI-E-ESTRAI.bat (capitolo 2).
  2. Sostituire la cartella dei sorgenti: chiudete GitHub Desktop. In Documenti\GitHub rinominate professore-digitale in professore-digitale-vecchia, poi spostate lì la nuova cartella professore-digitale. Riaprite GitHub Desktop: ritrova la cartella da solo (contiene già la versione nuova e l'indirizzo di GitHub).
  3. Spedire: in GitHub Desktop cliccate ⬆ Push origin (capitolo 4b). Se compare Fetch origin e nient'altro, cliccatelo e poi Push.
  4. Release: come il capitolo 6, con il nuovo numero (tag v3.6.0, file della cartella rilascio-3.6.0).
  5. Controllo: come il capitolo 7. Quando tutto funziona, la cartella professore-digitale-vecchia si può cancellare.
Solo contenuti nuovi o correzioni al sito?Se vi consegno solo un nuovo sito-X.Y.Z.zip (per esempio con un catalogo di modelli di IA aggiornato), aprite la Release della versione attuale → ✏ Edit → eliminate il vecchio sito-…zip con la ✕, trascinate il nuovo → Update release. Poi Actions → Pubblica il sito → Run workflow (campo vuoto = ultima Release) → Run workflow.

9 · Proteggere l'account GitHub

Da questo account dipendono gli aggiornamenti di tutti i PC che usano il Professore: va custodito come la chiave di casa.

  1. Verifica in due passaggi (2FA): su github.com, foto profilo → Settings → Password and authentication → Enable two-factor authentication. Si usa un'app sul telefono (es. Google Authenticator o Microsoft Authenticator) oppure una passkey. GitHub la chiede comunque a chi pubblica codice.
  2. Codici di recupero: alla fine GitHub mostra i recovery codes. Stampateli o scriveteli e conservateli insieme a questo libretto (non nel PC, non in una foto sul telefono). Senza codici e senza telefono l'account non si recupera più.
  3. Accesso con Google: avete creato l'account con Google, quindi la sicurezza dipende anche dall'account Google: tenete attiva anche lì la verifica in due passaggi.
  4. Email pubblica: i commit portano la firma Danilo D'Auria <danilodauria.site@gmail.com>, l'indirizzo già pubblico del progetto. Non attivate l'opzione «Block command line pushes that expose my email» (Settings → Emails), altrimenti GitHub rifiuterebbe i push.

Se qualcosa va storto

Cosa succedeCosa fare
UNISCI-E-ESTRAI.bat dice «ERRORE impronta»Una parte si è rovinata: chiedetemi di ricopiarla, oppure cancellate quella .parte e riprovate dopo averla ricevuta di nuovo.
GitHub Desktop: «Authentication failed» o chiede di accedereFile → Options → Accounts → Sign out, poi Sign in: si apre il browser, accedete con Google come al solito e autorizzate GitHub Desktop.
Push rifiutato con «refusing to allow an OAuth App to create or update workflow»Uscite e rientrate in GitHub Desktop (riga sopra): al nuovo accesso concede il permesso «workflow». Se persiste, ditemelo: si carica quel solo file dal sito.
Push rifiutato: «Updates were rejected… fetch first»Su GitHub c'è qualcosa che il PC non ha (es. avete modificato un file dal sito). Cliccate Fetch origin, poi Pull origin, poi Push origin. Se compaiono «conflicts», fermatevi e scrivetemi.
«GH001: Large files detected… exceeds 100 MB»Un file grande è finito nei sorgenti. Non forzate: scrivetemi, lo tolgo io dalla storia. (Con le cartelle che vi consegno non deve succedere.)
Actions: «Pubblica il sito» con ✘ rossoCliccatelo per vedere il passo fallito. «no assets match» = manca sito-X.Y.Z.zip nella Release: aggiungetelo (Edit) e poi Run workflow. «Pages not enabled / Get Pages site failed» = rifate il capitolo 5, poi Re-run all jobs.
Il sito dà «404 There isn't a GitHub Pages site here»Il robot non è ancora andato a buon fine (vedi riga sopra) oppure sono passati meno di 2–3 minuti. Il repository deve essere Public.
Il Professore non vede la nuova versioneControllate aggiornamenti.json nel browser (capitolo 7.3). Se lì c'è la versione giusta, aspettate qualche minuto: il sito ha una piccola memoria (cache).
«Scarica il nuovo pacchetto» dice «impronta non corrispondente»Il file nella Release non è quello consegnato (rinominato o scambiato). Edit della Release, eliminate il file e ricaricate quello della cartella rilascio-….
Ho sbagliato qualcosa nella ReleaseSi corregge tutto con ✏ Edit. Per rifarla da capo: Edit → Delete in basso, poi si ricrea con lo stesso tag. Il tag sbagliato si cancella da Releases → Tags.
